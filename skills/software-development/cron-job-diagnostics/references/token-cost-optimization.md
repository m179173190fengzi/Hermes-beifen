# LLM cron 任务的 token 成本：量化与瘦身

用户抱怨「太费 token / 充 10 块一天用掉一半」时走这份流程。别凭感觉砍功能，先量化。

## 1. 先量化

```bash
hermes insights --days 1
```

看四个数：`Sessions` / `Tool calls` / `Input+Output tokens` / `Total tokens`，
再看 `Notable Sessions` 里 **Most tokens** 和 **Most tool calls** 的 session 名（形如 `cron_<job_id>`）。
被点名的 job 就是成本源头，不用猜。

实测样例（4 条链上日报/天，DeepSeek）：

```
Total tokens: 7,570,236（一天）
单条日报: ~144,000 tokens，36 次工具调用
Most tool calls: 36 calls (cron_b4468ed62c8)
```

## 2. 成本结构：贵在「原料进上下文」，不在「写报告」

每轮对话都会重发完整上下文。一次工具调用返回几千行 `--raw` JSON，**会在该 session 的每一轮重复计费**。
所以：

> 减少「进上下文的原始数据量」的收益，比缩短 prompt 大一个数量级。

## 3. 改造模式：脚本预消化（script pre-digests → agent formats）

1. 写一个脚本干完所有**确定性**工作：拉数据 → 硬门槛淘汰 → 打分 → 同名去重 → 排序 → 拼摘要
2. 脚本只输出**紧凑摘要**（约 30-60 行），agent 只做叙事、跨链判断、排版
3. prompt 里写死：**「不要自己调 X 做扫描」**，并给出唯一数据来源命令（一行）
4. 限流/重试/退避全部放在脚本里 —— agent 不该为网络抖动付费
5. prompt 保留"数据源失败"分支：脚本报 `⚠️ <链> 数据源失败` 时如实说明，**禁止用旧数据或编造**

实测同一条日报改造前后：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 工具调用 | 36 次 | **1 次** |
| prompt 长度 | 4566 字 | 1440 字 |
| 进上下文的数据 | 几千行 raw JSON | ~30 行摘要 |
| 单次 tokens | ~144,000 | ~15,000 |

### 3.1 预消化后的新坑：agent 会「复算」脚本给的数字

实测事故：脚本输出 `11项 8/11`，agent 在交付的报告里写成 `11项 9/11? 实为 8/11` ——
它心里重算了一遍，还把自己的推导过程写进了交付物。数字没错，是**口径冲突**：
脚本按自己的规则算，prompt 里的"11 项"表述按另一套规则算，agent 试图调和就吐出自相矛盾的字符串。

对策（**先改脚本，别急着改 prompt**）：

1. 脚本在每个关键指标后标死口径：`11项 %d/%d(以此为准,勿复算)`
2. prompt 加一句：脚本数字为唯一口径，**不复算、不"更正"、不输出推导过程**；
   真发现不一致就按脚本写，末尾单独提一句"口径差异"
3. 交付前自检：读最终报告原文，grep `?|实为|应为|重新计算` —— 命中即复算痕迹

**一般化**：脚本预消化把 agent 变成"读者"，但 agent 天性会去校验读到的数字。
凡脚本算出来的分数/计数，必须在输出里显式标"权威口径"，否则调参过程会漏进交付物。

## 4. 其他杠杆（按收益排序）

1. **先砍频次**：4 条/天 → 2 条/天（暂停中间时段，保留早/晚盘）。一条命令、可随时恢复，用户最容易接受。
2. **no_agent cron**：watchdog / 阈值告警 / 余额检查 / 持仓刷新全部零 LLM 成本（脚本 stdout 直接投递）。
   阈值告警脚本要"越线才响、平时 stdout 为空"，否则会变成噪音源。
3. **压缩必须活着**：上下文压缩挂掉后只增不减 = 每轮都在为历史付费。
   （典型原因见 SKILL.md 的 `403 GROUP_DELETED` 一节。）
4. **长会话 `/new`**：上下文越长每轮越贵；分析型长对话结束后主动建议开新会话。
5. **prompt 瘦身**：有效但收益最小，放最后做。

## 5. 安全网

- 改 prompt 前先备份：把该 job 完整定义导出到 `~/.hermes/cron/prompts/backup-<job_id>-<date>.md`
- 批量改多条同款 prompt 走脚本（`jobs.json` → `hermes cron edit`），不要逐条手打
- 改完**必须真跑一次**（或次日首跑后立刻校对输出格式），别假设"prompt 改了就对"
- 摘要脚本要有自检输出：`过线 N 个｜硬门槛淘汰 M｜去重后 K` —— 数字异常（某链 0 候选）时先怀疑限流，
  而不是下"今天没有机会"的结论
