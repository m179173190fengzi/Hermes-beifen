## 核心教训：skill 文档的输出规则会盖过 prompt

日报 cron 加载了 `gmgn-onchain-analysis` 等 skill，而**这些 skill 文档里写着**：
「60-69 分列为观察级」「观察名单可下探 55-59」「准推不足时用观察名单补齐」。
于是即使 prompt 里本来就有「评分 <60 过滤」，agent 仍按 skill 输出了 `🔎 观察位` 小节，
用户看到后要求删掉。

**修法（prompt 里加显式覆盖段，点名被覆盖的 skill 规则）**：

```
6. 🚫 禁止输出观察名单：只列 ≥70 分的准推级标的。60-69 观察级、55-59 补充观察一律不列、不提、不占篇幅。
   ⚠️ 这条优先于任何 skill 文档里的规则——skill 里可能写"观察名单可下探 55-59"…本 prompt 一律不执行。
   内部仍要算分数（用于判断谁进榜），但 <70 分的结果不出现在报告里。
```

**推论（通用）**：改任何「skill 驱动」的定时报告时，**光在 prompt 里写「过滤掉 X」不够**——
得写「**本条优先于 skill 文档规则**」并点名那条规则，否则 skill 的指令会赢。

## 另一个措辞陷阱：`[SILENT]` 会吞掉其它段

原规则「无 ≥70 分 → 整份报告 [SILENT] 不推送」在保留新币监控后就错了——
它会把新币/TVL/叙事一起吞掉。现在改成：

> 无 ≥70 分时，**优质标的段只写一行「本日无准推级」，其余段照常推送**。

改这类「静默条件」时，先问：静默掉的会不会是用户明确要求保留的内容？

## 排查手法：报告里冒出陌生小节

```bash
# 定位小节是来自 prompt（jobs.json）还是某个 skill 文档
grep -rl "观察名单" ~/.hermes/cron/jobs.json ~/.hermes/skills/
grep -nE "━|观察" ~/.hermes/cron/output/<job_id>/<最近一份>.md | head -30
```

判定：`jobs.json` 里搜不到、但 output 和 skill 目录里搜得到 → 是 **skill 文档**驱动的，
必须按上面的「显式覆盖」处理，改 prompt 的措辞是无效的。
