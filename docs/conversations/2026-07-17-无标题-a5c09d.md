## LLM Wiki 摄入/导入机制 — 完整技术报告

### 1. HTTP API 端点（Tauri Rust 后端，端口 19828）

Rust 后端在 **`127.0.0.1:19828/api/v1`** 上运行一个 tiny_http 服务器。所有已注册的端点：

| 方法 | 路径 | 描述 |
|--------|------|-------------|
| GET | `/health` 或 `/api/v1/health` | 服务器状态、版本、auth/MCP 配置 |
| GET | `/api/v1/projects` | 列出所有已知项目 + 当前活动项目 |
| GET | `/api/v1/projects/{id}/files?root=wiki\|sources\|all` | 列出树形文件结构 |
| GET | `/api/v1/projects/{id}/files/content?path=wiki/foo.md` | 读取文件内容（仅允许 wiki/、raw/sources/、.llm-wiki 路径） |
| GET | `/api/v1/projects/{id}/reviews` | 列出审核项（支持 status/type/limit 过滤） |
| PATCH | `/api/v1/projects/{id}/reviews/{review_id}` | 更新单条审核 |
| POST | `/api/v1/projects/{id}/reviews/resolve` | 批量解决审核 |
| POST | `/api/v1/projects/{id}/search` | 全文+向量混合搜索 |
| GET | `/api/v1/projects/{id}/graph` | 知识图谱查询 |
| POST | `/api/v1/projects/{id}/sources/rescan` | 触发 Source Watch 重新扫描 |
| POST | `/api/v1/projects/{id}/chat` | 后端 Agent 聊天（40MB 消息限制） |
| POST | `/api/v1/projects/{id}/chat/{session_id}/cancel` | 取消正在进行的聊天 |

**没有专门的 `ingest` 或 `import` HTTP 端点。** 摄入通过 UI 操作（拖放、文件选择器、剪贴板服务器）或后台 Source Watch 触发的内部进程工作。

还有第二个服务器——**Clip Server（端口 19827）**：
| 方法 | 路径 | 描述 |
|--------|------|-------------|
| GET | `/status` | 健康检查 |
| GET/POST | `/project` | 获取/设置当前项目路径 |
| GET | `/projects` | 列出项目 |
| POST | `/projects` | 同步项目列表 |
| GET | `/clips/pending` | 弹出待处理剪辑（用于 Web Clipper 浏览器扩展） |
| POST | `/clip` | 接收正在摄入的新 HTML 剪辑 |

### 2. 文件格式支持

#### 可摄入的源扩展名（来自 `source-lifecycle.ts`）

`INGESTABLE_SOURCE_EXTENSIONS`:
```md, mdx, txt, pdf, doc, docx, pptx, xlsx, odt, odp, ods,
xls, csv, json, html, htm, rtf, xml, yaml, yml, epub, mobi
```

**是的——同时支持 JSON 和 Markdown。** JSON 文件被归类为 `data` 类型，由 Rust 文件系统命令作为 UTF-8 文本读取，并进入与 Markdown 相同的两步 LLM 摄入流水线（分析→生成）。

#### 文件类别映射（来自 `file-types.ts`）

| 分类 | 扩展名 |
|----------|-----------|
| markdown | md, mdx |
| text | txt, rtf, log |
| code | js, ts, py, rs, go, java, c, cpp, sh, html, xml, yaml, toml 等。 |
| image | png, jpg, gif, webp, bmp, svg, avif, heic |
| video | mp4, webm, mov, avi, mkv |
| audio | mp3, wav, ogg, flac, aac |
| pdf | pdf |
| document | doc, docx, xls, xlsx, ppt, pptx, odt, epub, mobi, pages |
| data | **json**, jsonl, csv, tsv, yaml, yml, ndjson |

所有 text/code/data/markdown 类型均作为 UTF-8 文本读取。PDF 和 Office 文档由 Rust 后端（pdfium、calamine、office_oxide）提取。EPUB/MOBI 通过专用的 ebook 提取器处理。

### 3. MCP 服务器能力

MCP 服务器（TypeScript，`mcp-server/`）不做直接摄入——它代理本地 API。可用工具：

| MCP 工具 | 功能 | 是否支持写入 |
|------------|---------|---------------|
| `llm_wiki_status` | 健康 + 当前项目摘要 | 否 |
| `llm_wiki_projects` | 列出已知项目 | 否 |
| `llm_wiki_set_project` | 将会话固定到一个项目 | 是（绑定） |
| `llm_wiki_files` | 列出文件树（wiki/，sources/，all） | 否 |
| `llm_wiki_read_file` | 通过 API 安全列表读取文件 | 否 |
| `llm_wiki_reviews` | 列出审核项（默认：未解决） | 否 |
| `llm_wiki_search` | 关键词/向量混合搜索 | 否 |
| `llm_wiki_chat` | 后端 Agent 聊天（mode: fast/standard/deep/local_first） | 否（仅读取） |
| `llm_wiki_graph` | 知识图谱查询 | 否 |
| `llm_wiki_rescan_sources` | 通过 Source Watch 规则触发重新扫描 | 是 |

**MCP 没有写入新源的直接工具。** 要摄入外部数据，您需要通过 MCP 的 `llm_wiki_chat` 发出命令（例如，“导入此 JSON”）或用脚本写入 `raw/sources/` 并调用 `llm_wiki_rescan_sources`。

### 4. 摄入流水线（引擎室）

摄入是两步 LLM 链式思维过程：

#### 步骤 1：分析
```
源文件 → SHA256 缓存命中检查（跳过，如果不变）→
LLM 分析提示（提取实体、概念、参数、与现有 wiki 的连接、矛盾）→
结构化的 JSON 分析
```

#### 步骤 2：生成
```
分析 + 当前 wiki（index.md、purpose.md、schema.md）→
LLM 生成提示 → FILE 块（---FILE: wiki/xxx.md--- ... ---END FILE---）→
解析并写入项目 wiki/ 目录
```

**关键细节：**
- **SHA256 缓存**：`ingest-cache.ts` —— 对源内容进行哈希处理。如果哈希匹配且所有先前写入的文件仍存在于磁盘上，则跳过。
- **持久队列**：`ingest-queue.ts` —— 任务序列化处理，保存到 `项目/.llm-wiki/ingest-queue.json`，崩溃后恢复，最多重试 3 次。
- **源溯源**：每个 wiki 页面在其 YAML 前置元数据中获得一个 `sources: []` 字段。
- **文件块解析**：`ingest.ts`（`parseFileBlocks`）—— 健壮的解析器，处理 Windows CRLF、流截断、空格变体、围栏内的字面 `---END FILE---` 标记以及路径逃逸预防。

### 6. `raw/sources/` 目录结构规范

这是预期的项目布局：

```
<project-root>/
├── raw/
│   └── sources/           # 不可变的原始源文件
│       ├── <topic>/       # 可选子文件夹
│       │   ├── doc1.pdf
│       │   ├── doc2.md
│       │   └── ...
│       ├── scheduled-import/  # 自动在 scheduled-import 监控下创建
│       │   └── ...
│       └── .cache/        # 预处理的文本缓存（自动管理）
│           ├── doc1.pdf.txt
│           └── ...
├── wiki/                  # LLM 生成的 wiki 页面
│   ├── index.md           # 内容目录
│   ├── overview.md        # 全局摘要（每次摄入后自动更新）
│   ├── log.md       …(截断)```

**关键规则：**
- 源文件放入 `raw/sources/` 以进行摄入
- 每个源文件最后在前置元数据中生成具有 `type: source-summary` 的 `wiki/sources/<slug>.md`
- 通过 `importSourceFolder()` 从外部导入的文件被复制到 `raw/sources/<folder-name>/`，保留目录结构
- 从 URL 导入的文件作为 `.html` 或 `.txt` 保存到 `raw/sources/`，并附加源 URL 元数据
- **已排除**：点文件、`.git/`、`node_modules/`、`__pycache__`、`.cache/`、`.obsidian/` 以及可配置的扩展名/globs

### 7. 数据摄入有三种方式

| 方法 | 机制 | 效果 |
|--------|-----------|--------|
| **UI 拖放 / 文件选择器** | 内部 Tauri 命令 | 复制到 `raw/sources/`，排队摄入 |
| **UI 文件夹导入** | `importSourceFolder()` | 将整个文件夹树复制到 `raw/sources/`，带入文件夹上下文 |
| **URL 导入** | `importSourceUrls()` | 获取 HTTP(S) 内容，保存到 `raw/sources/`，排队摄入 |
| **Source Watch（自动）** | `scheduled-import.ts` | 监控目录，复制新/更改的文件，排队摄入 |
| **Web Clipper（浏览器扩展）** | Clip Server（端口 19827）| 存储剪辑，前台轮询并摄入 |
| **剪贴板 PDF** | Clip Server + PDF 处理 | 从系统剪贴板提取 PDF 文本 |

### 8. 外部 JSON 数据（如 topics.json）的摄入过程

鉴于 `topics.json` 是这样的结构：
```json
[
  {"id": "os-design", "title": "操作系统设计", "related": ["kernel", "scheduling"]},
  ...
]
```

通过 LLM Wiki 摄入它的方式是：
1. **将文件放入 `raw/sources/`**（拖放或复制）
2. **JSON 作为 UTF-8 文本读取**（`data` 文件类别）
3. **两步 LLM 流水线**：
   - 步骤 1（分析）：LLM 读取 `topics.json` 作为纯文本，提取实体、概念、连接
   - 步骤 2（生成）：LLM 写入 wiki 页面（实体、概念、索引、概述），并在 `sources: ["topics.json"]` 前置元数据中链接回原始 JSON
4. **wiki 页面现已可搜索、可查询，并连接到知识图谱**

**建议的自动导入工作流程：**
- 运行一个脚本，将您的 JSON 复制到观察目录中并调用 Source Watch rescan
- 或使用 `llm_wiki_chat` MCP 工具发送“我已将 topics.json 放入 raw/sources/，请为其运行摄入”
